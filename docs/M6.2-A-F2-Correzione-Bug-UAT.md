## 1. Diagnosi riproducibile

### BUG 1 — Pianificazione non abilitati

Non è stata dimostrata una creazione server abusiva semplicemente dalla presenza di “Nuovo Accesso Emporio”. Prima delle modifiche F2, il gruppo HTTP reale F1 passa **30/30** sul PostgreSQL sintetico: diritto assente, sospeso, revocato e Area incompatibile sono già negati.

Il difetto UX riprodotto è nella scheda Beneficiario: il link “Pianifica accesso” era subordinato al Credito Solidale, non all'abilitazione Emporio corrente. Inoltre il GET dell'abilitazione restituiva lo stato registrato `attivo` anche con `data_effetto` futura, mentre l'operatività server lo negava. La presentazione non distingueva quindi “registrato attivo” da “effettivamente attivo”.

Correzione: stato effettivo SQL comune, comprendente `programmato`, utilizzato da letture dettaglio/batch, filtri di ricerca e guardia transazionale. Accessi e Cassa condividono inoltre il predicato operativo anagrafica/abilitazione/credito/Centro coerente. Le guardie correnti sui comandi, grant, Area e Magazzino rimangono; nessun bypass frontend o inventariale. La scheda permette la pianificazione e le azioni operative sul credito solo con stato effettivo attivo. Saldo e storico restano consultabili secondo grant. Durante refetch/errore della ricerca o debounce non concluso, una vecchia selezione non abilita il salvataggio.

### BUG 2 — Stato assente nella directory

La pagina `beneficiari.tsx` non aveva query né colonna Emporio; il solo riepilogo Mensa non poteva rappresentare un servizio indipendente.

Correzione: colonna Emporio accanto a Mensa, richiesta batch per gli ID della pagina corrente (massimo 100), un unico join con abilitazione Beneficiario×Area attuale, nessuna HTTP per riga. Il server applica grant corrente e scope della directory Sociale, senza ampliare globalmente l'anagrafica. Il DTO non espone saldo, motivi o dossier. Nessuna riga di abilitazione significa `non_abilitato`; una query in errore o un ID non restituito mostra `-`, non inventa un'abilitazione. Adeguati skeleton e colspan. Cache separata per contesto autenticato e ID della pagina; transizioni invalidano riepilogo, scheda, directory e ricerche operative.

### BUG 3 — Nome escluso premendo Invio

In `emporio-accessi.tsx`, Invio impostava sempre `cardSearch=true`: `Rossi Anna` diventava `codiceTessera=Rossi Anna`. Il beneficiario presente e correttamente restituito da `search=Rossi Anna` veniva escluso dal successivo filtro di tessera esatta. Non è stato necessario ripristinare un filtro permissivo sul Centro: F1 aveva già introdotto lo scope Emporio per Area.

Correzione: Invio conserva la ricerca generale; il server segnala soltanto la corrispondenza esatta di una tessera valida. La selezione automatica richiede un solo risultato identificato da codice Beneficiario esatto oppure tessera valida, mai un semplice nome. Lo scanner esplicito mantiene la ricerca card-only. Verificato anche un codice USB opaco registrato, non solo il prefisso `MS-`.

Fixture reale: Area A, operatore Centro 1, beneficiario Anna Maria Rossi Centro 2, Emporio Centro 3; credito operativo valido e diritto esplicito. DB → diritto → ricerca HTTP → query `search` → opzione visibile → selezione → POST 201 verificati. Nessuna modifica al Centro di origine; preferenza Emporio non sovrascrive la scelta. Gli ID della preview dell'utente non sono usati per creare fixture.
